# v5 — hand the knowledge system to its own plugin

**What changed:** `work` no longer owns or scaffolds `domains/**`. The knowledge system is a
separate plugin's, and `work` reads it through the doc-system seam instead of assuming it exists.
Nothing in `domains/` moves or changes shape — this is an **ownership** change.

**Preconditions:** the bus has its three shared sections (v3) and lives at `.agent/PROJECT.md`
(v4). Decline with "waiting on v4" otherwise.

**Apply (v4 → v5):**

1. **Hand over the `knowledge` rows, do not delete them.** In `## Commands`, if the `knowledge`
   row still reads *"n/a — owned by `work`"*, replace it with `| knowledge | domains migrate |
   domains init |`. That is the one row `work` may write about another role, and only because
   `work` is the outgoing owner recording where the role went — after this, the row is theirs.

   **If there is no `knowledge` row in `## Commands`, add none.** This is the case for every
   project that arrived here through v3, which seeds the table with the `delivery` row and
   nothing else, so there is no handover to record. Writing the row anyway would be `work`
   declaring a command for a plugin that may not be installed — the exact guess `## Commands`
   exists to prevent. An absent row is a complete answer: a doctor reads it as "`knowledge` is
   stale and its migrate command is not available here", and `domains` writes its own row the
   first time it runs.

   Leave the `## Artifacts` knowledge row exactly as it is — the path is still correct, and its
   new owner re-registers on its own schedule.

   **Add no `knowledge scaffolding` row to `## Versions`, and do not correct one that is there.**
   `work` has no number to write: the knowledge system's version is its owner's, in its owner's
   scheme, and a value carried over from `work`'s would read as newer than that owner's canonical
   and skip its first real migration. If an older bus already carries such a row, it is not
   `work`'s to edit on the way out; say that its owner will re-stamp it, and leave it.

2. **Do not touch `domains/` at all.** No reformatting, no re-registering, no INDEX rewrite. If
   the folder is absent, do nothing — its absence is not this migration's problem.

3. **Leave the `Domain Knowledge System` section of `CLAUDE.md` alone**, including the
   `prep`-related Rules bullet. Both belong to the knowledge plugin now. Removing them would
   break `prep` for a project that has a working knowledge system and has not installed the new
   plugin yet — the upgrade path is *install it*, not *lose the docs*.

4. **Tell the user what changed for them**, in one line each, and only what applies:
   - `domains/` exists → *"project memory is now a separate plugin; install it to keep knowledge
     loading and to run `prep refresh`."*
   - `domains/` does not exist → nothing. There is nothing to lose.

⚠️ **This migration removes a capability from a repo that has one.** It is additive on disk and
subtractive in behaviour, which is exactly the case a silent migration would get wrong.
