# v4 — move the config bus and `work`'s artifacts out of `domains/`

**What changed:** The config bus moved to **`.agent/PROJECT.md`** — one place, always, for every
tool in the stack. `work`'s own artifacts moved with it: the overlay to
**`.agent/work/workflow.md`** and its extracted rules to **`.agent/work/rules/`**. `domains/`
keeps the knowledge system and nothing else, because a tool writing inside another tool's folder
is what disjoint ownership forbids.

**Preconditions:** the bus has its three shared sections — `## Artifacts`, `## Versions`,
`## Commands` (v3). If they are absent, decline and say "waiting on v3"; the orchestrator will
retry after v3 applies.

**Apply (v3 → v4):**

1. **Move the bus.** `git mv domains/PROJECT.md .agent/PROJECT.md` (create `.agent/` if needed).
   Use the VCS's move so history follows the file. If `.agent/PROJECT.md` already exists, **stop
   — two buses is a state no migration may resolve by guessing which is real — and then give the
   user the means to resolve it**:

   1. Show what actually differs: the sections each file has, and for sections both have, the
      rows whose values disagree. Say which file each value came from. A user cannot choose
      between two paths; they can choose between two sets of values.
   2. Offer, and apply what they pick: **keep `.agent/PROJECT.md`** and delete the legacy file;
      **keep the legacy file**, replacing `.agent/PROJECT.md` with it; or **stop here** so they
      can reconcile the two by hand and re-run — this migration is a no-op once one of them is
      gone.
   3. Never merge them yourself, even when the diff looks trivial. Two buses means two tools
      wrote configuration in two places, and which value is current is a fact about their
      project that neither file records.

2. **Do not leave a pointer stub** at `domains/PROJECT.md`. Two reasons, and both matter more
   than the convenience:
   - The **legacy-path shim** reads that exact path when `.agent/PROJECT.md` is missing. A stub
     there is a file the shim could read *as configuration*, and "helpful note" is not a shape it
     knows how to reject.
   - After the knowledge system changes owner, a file `work` left in `domains/` is `work`
     writing inside someone else's artifact.

   The human-facing pointer belongs in the generated `CLAUDE.md` section (step 5), which is
   already `work`'s to write.

3. **Move the overlay, if the project has one.** `git mv domains/workflow.md
   .agent/work/workflow.md`. Then move any extracted rules: every
   `.claude/rules/workflow/*.md` → `.agent/work/rules/*.md`, and remove
   `.claude/rules/workflow/` if it is now empty. Leave the rest of `.claude/rules/` alone — it is
   the project's.

4. **Repoint the references the move just broke — and nothing else.** The overlay names its
   extracted rules by path, and the rules cross-reference each other and the overlay, so a pure
   `git mv` leaves a set of files pointing at paths that no longer exist. In the moved overlay,
   the moved rules, **and the bus's own rows** — all three are `work`'s own files — replace
   `domains/workflow.md` → `.agent/work/workflow.md` and `.claude/rules/workflow/` →
   `.agent/work/rules/`.

   The bus is easy to forget because the move did not touch it, but its `Workflow overlay` row
   names the overlay's old path, and a later migration that reconciles that row against
   `## Artifacts` will find two different real paths and **stop**, which is the correct
   behaviour for a contradiction and a bad way to discover this one. Repointing the row here is
   the same substitution in the same owner's file.

   This is a **path substitution, not an edit**: after it, every line that is not one of those
   references must be byte-identical to what the move produced. It is also the *whole* of what
   this migration may do inside the overlay — its schema and its content have their own version
   and their own upgrade path (`work update-workflow refresh`), and this migration does not touch
   either.

   ⚠️ **Tell the user this one changes behaviour, not just location.** `.claude/rules/**` may be
   loaded ambiently by the harness; `.agent/work/rules/**` is not. The overlay references these
   files explicitly, so they still load when a step needs them — but they stop being ambient
   context for every session, which is a saving and a change.

5. **Update the `## Artifacts` rows** in the moved bus to the new paths — a `Ticket flow` row
   that named `domains/workflow.md` becomes `.agent/work/workflow.md`. **A row reading `none`
   stays `none`**: no overlay existed, and moving one that was never written registers a file
   that does not exist (v15 repairs projects where this step did that). Leave every other row alone, including rows owned by roles
   that are not installed: this migration moves `work`'s artifacts, and rewriting another owner's
   row would be editing content rather than relocating it.

6. **Rewrite the generated `CLAUDE.md` section** so its paths point at the new locations, and
   make sure it names `.agent/PROJECT.md` as the config bus. Touch only the section `work`
   generated — never the user's own prose.

7. **Say that things outside this repo now point at the old paths.** One line, at the end:
   *"Anything outside this repo that named the old paths is now stale — your auto-memories,
   personal notes, saved commands, bookmarks. No migration can reach them."*

   This is not hedging. A doctor run on a migrated repo found a memory instructing agents to
   keep `domains/PROJECT.md`'s Verification row accurate — a file this migration had deleted,
   in a store outside the repo that nothing here can edit. The stale reference then outlives
   the migration and keeps steering sessions at a path that no longer exists. Naming it costs a
   sentence at the one moment somebody is paying attention to these paths.

   Do not go editing them. They are user-authored and outside the repo, which puts them outside
   what a reviewed diff can cover.

8. **Re-read before re-stamping.** After the moves, confirm the bus is readable at its new path
   and its sections are intact. Only then does `migrate.md` step 7 stamp — a stamp written
   against a file that did not survive the move is the one outcome nothing else can detect.
