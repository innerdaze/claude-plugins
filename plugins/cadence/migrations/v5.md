# v5 — the Definition of Done row

**What changed:** the bus's `## Verification` section gained a `Definition of Done` row (cadence
2.0.3) — a `path`, or `path#heading`, naming the document where the project's bar is written in
its own words. Session end judges each declared check against it and the delivery skill plans
against it. `/cadence:init` writes it on a fresh project; a project initialised before 2.0.3 never
got it, and this migration is how it does.

**Preconditions:** the bus is at `.agent/PROJECT.md` and has a `## Verification` section
(delivery v10). Absent → decline with "waiting on the bus".

**The row is `shared`.** Write it only when absent or blank; never overwrite a value, whoever
wrote it. The delivery tool reads the same row and has no migration for it — whichever owner's
command runs first writes it, and the other finds it present.

**Which file is the bar is the person's answer, not this migration's.** So steps 3–5 ask, and
apply what they choose. That does not break *two developers, one diff*: the answer is committed
with the stamp, and the stamp makes a second run a no-op.

**Apply (v4 → v5):**

1. **Read the row.** Present with a value → nothing to do; go to step 6.

2. **Look for candidates**, in the tracked tree: a file whose name says *definition of done*
   (`DEFINITION_OF_DONE.md`, `definition-of-done.md`, …), and a heading reading *Definition of
   Done* outside fenced code in a process, contributing or feature-process document. Each
   candidate is a `path` or a `path#heading` — the heading's **exact text**, never a slug, and
   resolved by `${CLAUDE_PLUGIN_ROOT}/checks/BUS-CHECKS.md` § *`## Verification → Definition of
   Done` resolves* before it is offered. **A file holding more than one checklist** — an
   epic bar beside a ticket bar — is offered as the heading for the ticket bar, never as the
   whole file.

3. **Exactly one candidate** → propose it: *"`docs/DEFINITION_OF_DONE.md` looks like this
   project's Definition of Done — record it in the bus so sessions judge checks against it?"*
   Yes → write the row. No → step 5.

4. **More than one** → list them, each with its first few items, and let the person pick one or
   none. One → write the row. None → step 5.

5. **No candidate, or none chosen:**
   - **`config.dod_gates` is set, or the flow's `gates.dod.checks` is non-empty** → run
     `/cadence:init`'s *No document anywhere, and gates declared* step
     (`${CLAUDE_PLUGIN_ROOT}/skills/init/SKILL.md` § *Definition of Done*) — and only that
     step. It offers to write the document from the declared checks, never adding one that is
     not declared, and writes the row with it. Writing a document is authoring, which is init's;
     this migration reaches it rather than repeating it.
   - **They decline, or there is nothing declared** → leave the row absent. Say in one line what
     that costs — every check is judged from its name alone, and the delivery skill plans without
     a bar — and that `/cadence:doctor` will keep reporting it until someone answers.

6. **Compare, when a document is now registered.** Items the document lists that neither the flow
   nor `config.dod_gates` declares are *written but not gated*: name each and the one-line
   `dod_gates` entry that would gate it. **Add none of them yourself** — a gate is a commitment
   every future session must meet, and that is the person's call. Report only.

7. **Stamp** — after asking, whatever the answer. The migration's job was to put the question;
   an open answer is the doctor's to keep raising, not a reason to hold the stamp back and ask
   again on every run.

`[note]` The doctor used to say *"no migration can write the row: which file is the bar is a
question for a person"*, and named `/cadence:init` as the only remedy. A migration may ask — the
delivery tool's migrations already do — so a project upgraded across 2.0.3 now gets the row from
the command that upgrades it. Found on a real upgrade, which ended by telling the person to run
init.
