# Cadence Adapters — the bindings API

*An **adapter** is an instruction doc a skill loads to actually perform an operation against a project's tools. Adapters are the **doers**: where hooks decide and describe, adapters carry out side-effects (create a ticket, make a commit, write a doc). A skill picks the adapter by the `kind` field in the project's config, e.g. `config.tracker.kind: linear` → the `linear` tracker adapter. This file is the versioned contract every adapter must satisfy.*

## Where adapters live — Cadence assumes no environment

The plugin ships **no integration for any specific external tool.** Shipping a `linear`/`jira`/`diversion` adapter would bake in assumptions about tools an adopter may not have, and about interfaces that vary between installs (two Linear MCPs can expose different namespaces and verb names). Instead, adapters come in three tiers:

| Tier | What | Where it lives |
|---|---|---|
| **Contracts** | this file + the family operation lists below | shipped in the plugin (fully agnostic) |
| **Fallbacks** | `markdown` (tracker), `git` (vcs), `none` (docs) | shipped — but only the *default* when `init` detects plain files / git; not assumed |
| **Environment adapters** | `linear`, `github`, `jira`, `diversion`, a `domains` doc-system, … | **project-local, generated by `/cadence:init`** against the tool actually present, stored in the project |

**Resolution order** for a `config.<family>.kind`:
1. a project-local adapter at `.agent/cadence/adapters/<family>/<kind>.md`, else
2. the shipped fallback of that kind (`markdown` / `git` / `none`), else
3. error → tell the user to run `/cadence:init` to generate the adapter.

So the plugin stays portable and small: it carries the **method** and the **contracts**, and binds to a project's real environment only through adapters that `init` writes against what it finds. The fallbacks are the one thing that runs out-of-the-box, because they assume ~nothing (a filesystem, and git).

*(A distribution MAY include clearly-marked **reference examples** under `adapters/examples/`, used only as seeds when `init` detects a matching tool. They are documentation, never the active binding. The base plugin ships none.)*

## The item record

Every tracker speaks in items. These are the fields a skill may ask for:

| Field | Required | Used by |
|---|---|---|
| `id` | **yes** | everything |
| `title` | **yes** | everything |
| `type` | **yes** | `hierarchy.levels`, `bug.triage` |
| `status` | **yes** | the state machine |
| `epic` | no | `current-epic` priority token |
| `milestone` | no | `next-roadmap-ticket`, roadmap progress |
| `labels` | no | context loading via the doc adapter's `taxonomy()` |
| `assignee` | no | **goal selection** (ownership), `wip_limit: per-person`, ceremonies *(deferred)* |
| `cycle` | no | `committed-sprint` token; sprint flows |
| `order` | no | `backlog-by-rank` token |
| `depends_on` | no | `blocker-for-current-ticket` token |
| `severity` | no | `customer-bug-by-severity` token |
| `updated_at` | no | `updated_since` filters, roadmap progress |

**An optional field a tracker cannot store is not an error.** The adapter
declares it unsupported, and any step needing it is skipped with a note — the
priority policy degrades one token at a time rather than guessing. What is
forbidden is inventing the data.

## Capability declaration

Every adapter states, near the top, which optional operations and fields it
supports. This is what makes degradation *visible* instead of silent, and it is
the first thing `/cadence:doctor` reads:

```markdown
## Capabilities
supports:    list_closed(), update(), statuses(), order, depends_on
costly:      depends_on            # writable, but only readable one item at a time
unsupported: cycle, assignee, severity   # this tool has no such concept
```

**`costly` is a third state, and real adapters need it.** A field can be writable
while being unreadable in bulk — Linear accepts `blockedBy` on a write but its
list query returns no relations, so reading dependencies across a backlog costs
one call per item. That is neither "supported" (a skill would evaluate it over
fifty items without thinking) nor "unsupported" (the data is genuinely there). A
skill seeing `costly` should narrow the candidate set first, or hand the sweep to
the `mechanical` subagent, rather than either fanning out blindly or silently
skipping the field.

A skill that needs an unsupported capability says so once and continues without
it. A skill must never work around a missing capability by writing the data
somewhere the tool doesn't model.

## Tracker contract

A tracker adapter manages work items. Required:

- **`statuses()`** → the statuses this tracker **actually accepts**. Return `{name, id?, category?, terminal?}` per status — `id` and `category` wherever the tool has them, because **a name is not guaranteed to be unique**. This is the primitive the whole status layering rests on: `/cadence:init` builds `config.tracker.status_map` from it, `/cadence:doctor` re-checks the map against it, and `set_status` validates against it. If a tool genuinely cannot enumerate its statuses, declare `statuses` unsupported — init then asks the user once and records the list in config.

  **Report `category` faithfully where the tool has one.** It is how `/cadence:init` drafts a starting `status_map` for the user to correct, and how `list_open` knows a status is terminal without being told. Pass through the tool's own classification rather than a tidied-up version of it: a board with two `started` states should report two, because that irregularity is exactly what the user needs to see before confirming a mapping.

  **Duplicate names are normal and must be handled, not assumed away.** Linear, Jira and GitHub Projects all let two states share a display name across different categories — a real board was observed with two states both called `Queued`, one `backlog` and one `unstarted`. A `status_map` entry must therefore resolve to **exactly one** status. Where a bare name is ambiguous, the entry carries a qualified form the adapter can resolve unambiguously:

  ```yaml
  status_map:
    Backlog: { name: Queued, category: backlog }   # disambiguated
    Todo:    { name: Queued, category: unstarted }
    Done:    Shipped                                # a bare name is fine when unique
  ```
- **`list_open(filter?)`** → items not in the terminal set. `filter` may carry `{milestone, epic, assignee, cycle, type, status_in, status_not_in, updated_since, limit}`; ignore filter keys for fields you don't support, and say which you ignored.

  **The terminal set is the union of what the flow declares and what the tracker knows.** The flow's `done` + `abandoned` roles say which lanes *Cadence drives* items into. But a tracker often has finished states the flow never models — a Linear board carries `canceled` and `duplicate` categories whether or not the flow has an `abandoned` role. Those items are finished, and `list_open` must exclude them. Counting a cancelled ticket as open work would resurface it as a candidate goal forever. Where the tool reports a status as terminal, believe it.
- **`get(id)`** → one item's full record (fields + description + comments).
- **`create(fields)`** → create an item; return its new `id`.
- **`comment(id, text)`** → append a comment.
- **`update(id, fields)`** → change any writable field. **`set_status(id, status)`** is documented sugar for `update(id, {status})`.
- **Concept mapping** — how this tracker represents `epic`, `milestone`, and `label`. This is also where `epic_convention` lives: how a tool models an epic is a fact about the *tool*, not about your project, so it belongs in the adapter and not in config.

Optional:

- **`me()`** → who the current user is on this tracker, as whatever identity `assignee` carries
  (an account id, a username, an email). Most hosted trackers know this from the token; the
  operation exists so a skill never has to ask a person who they are or guess from a git email.
  Unsupported is fine and common — see *Ownership* below for what a skill does then.
- **`list_closed(filter?)`** → terminal items. Needed by `session_state.prune` (to tell what's really finished) and by roadmap milestone progress.
- **`list_cycles()` / `current_cycle()`** → for sprint flows. Unsupported degrades to milestone scope.
- **`search(text, filter?)`** → open items whose title or body match `text`, with the same `filter`
  keys as `list_open`. Used by `/cadence:plan` to find existing work **before** it creates any — a
  skill's own operation that no hook can rely on and no flow can declare, so adding it moved no
  contract number. Unsupported degrades to `list_open()` filtered by the caller, and says so.

**`set_status` must resolve to exactly one status, or refuse.** If the target
matches no status in `statuses()`, stop and report it — never approximate to a
similarly-named column, and never create one. If it matches **more than one**,
also stop: an ambiguous target is not a licence to pick the first. Say which
statuses matched and that `status_map` needs the qualified form. Cadence does not
modify the shape of your board, and it does not guess which half of an ambiguity
you meant.

*Reserved, deliberately not in the contract yet:* a general history/audit
operation. Its only consumer is the postmortem timeline inside the deferred
ceremony layer, most trackers cannot answer it uniformly, and a contract
obligation with no caller is exactly the kind of dead weight this contract is
being cleaned of.

## VCS contract

- **`status()`** → the working-tree state (clean / list of changed files).
- **`diff(paths?)`** → the diff for review / message-drafting.
- **`log(n?, paths?)`** → the last `n` checkpoints as `{ref, message, item_refs}`. Needed to verify that a checkpoint referencing a given item exists — which `/cadence:session end` requires and previously had no way to do.
- **`add_untracked(paths)`** → stage new/untracked files (some VCS need this explicitly).
- **`checkpoint(message, item_ref)`** → create a commit whose message references `item_ref`. Never push unless asked.
- **`ignore(paths)`** → append paths to the ignore file the `kind` implies (`.gitignore` / `.dvignore` / …), idempotently. Used at init to keep Cadence's local session-state file out of the repo.

## Doc-system contract

- **`locate(topics)`** → which existing docs a skill should read before working on those topics (may be empty).
- **`record(note)`** → persist a durable gotcha/convention where the project keeps knowledge.
- **`taxonomy()`** → the project's label vocabulary: the set of context labels an item can carry, so the execution skill can load the right docs from an item's labels alone. **May be empty** — that's a normal answer, not an error. This is where a doc system's structure becomes tracker labels (a `domains` adapter returns its INDEX headings; `none` returns nothing).

## Intent-read contract — consumed, never owned

Cadence **consumes** the intent-read seam the way `work` does; it owns nothing here. The contract
belongs to the intent tool. What cadence needs from it is one question — *does this milestone, or
this proposed item, contradict anything the maintainer has stated?* — and it asks that question in
`/cadence:plan` (before breakdown, and again over the proposed items) and `/cadence:roadmap` (when a
milestone is drafted or revisited).

- **`locate(topics, paths?)`** → ranked stated intent that applies, **with attribution markers
  intact**. Required at every tier: a layer that cannot say what applies is not answering its only
  question.
- **`check(plan)`** → what a plan contradicts — the statement, the clashing part, why — and **never
  a verdict**. May be `unsupported`; the shipped fallback says so, and the skill does the same
  comparison from `locate` in the proposal a person reads.
- **There is no write operation, at any tier.** Not `record`, not "note that a milestone
  disagreed". The layer's first rule is that the code gets no vote, and a tool that could edit the
  thing it is measured against would edit it at the moment it was found wrong. A contradiction is
  reported outward and ruled on by a person.

**Resolution** is the same as every other family: the bus's `## Bindings` → `Intent` row names the
kind; a project-local adapter at `.agent/cadence/adapters/intent/<kind>.md` outranks the shipped
`${CLAUDE_PLUGIN_ROOT}/adapters/intent/<kind>.md`; no row means `none`. **The folder comes from the
`## Artifacts` row whose Owner is `intent-layer`** — matched on the role id, never on a name, and
never guessed from a folder that looks like design documentation. Cadence writes neither row: both
belong to the intent tool's own init.

**`none` is the normal case and says nothing.** Most projects have no intent layer. The one place
the absence is stated is the proposal's *Intent conflicts* section, which reads *"none — this
project has no intent layer"* so nobody downstream mistakes silence for a pass.

## Where adapter data lives

Everything Cadence owns sits under **`.agent/cadence/`** — the config, generated adapters, a custom flow, and any data a fallback adapter needs. Nothing is written outside that root (the sole exception is a call to the VCS adapter's `ignore()`, which by definition must edit the project's ignore file).

Within that root there are two kinds of file, and the difference is whether the project's collaborators need it:

| | Examples | Committed? |
|---|---|---|
| **Shared** — project state a teammate or a future you must see | `config.md`, `adapters/**`, `*.flow.md`, `backlog/**` (the `markdown` tracker), `notes.md` (the `none` doc adapter) | **yes** — versioned alongside the code |
| **Local** — one author's working scratchpad, in this working copy | `.agent/local/cadence-session.md` | **no** — the whole of `.agent/local/` is ignored, added at init via `ignore()` |

**The directory marks the second kind**, not a filename suffix. One ignore entry covers
everything uncommitted, which matters because the previous convention needed an entry per file:
an ignore line that has stopped matching looks exactly like one that works, and v1 of this
plugin's migration exists partly to repair one. It is also **not shared between worktrees**, so
two checkouts of one repo no longer overwrite each other's session. The split matters most for the `markdown` tracker: its items are *meant* to be committed, so a backlog diffs and reviews like code — that's the main reason to choose it over a hosted tracker on a small project. Session state is the opposite: high-churn, single-author, and a guaranteed conflict on any shared branch.

## The one store Cadence owns — `session_state`

Everything else Cadence touches, it reaches through an adapter. This file is the
exception: there is no external tool behind it, so the plugin owns the format.

It is a **scratchpad for what the tracker cannot tell you**, and its value comes
entirely from staying small. A large session-state file is not a richer memory —
it is a second, stale copy of the backlog that disagrees with the real one while
looking authoritative. Hence a fixed, deliberately thin schema and a stated
budget:

```markdown
# Session state — <project>
updated: <YYYY-MM-DD>

## Goal
current: <item-id> — <one line, or "none">
next:    <item-id> — <one line, or "none">

## Traps
- <item-id or area>: <the non-obvious thing that would be re-broken by someone
  reading only the ticket>

## Milestone note
<at most a couple of lines on where the milestone actually stands, when that
differs from what the tracker implies>

## Tree at start
<`clean`, or the paths `status()` reported dirty when this session began — one per
line, nothing else. Written by start, read by end's checkpoint, cleared by end.>
```

**Budget: about 40 lines.** Past that, `session_state.prune` is under-pruning —
the fix is to delete, not to extend the schema. `## Tree at start` is exempt in
spirit — it is a snapshot for one session, not memory — but a long one is itself a
finding: a working copy that dirty at start is being shared with something. Anything durable belongs in the
doc system via `record()`; anything about one item belongs on that item.

A **trap** is the only thing that survives its item being closed, and it has a
specific shape: *the shipped work deliberately departs from the ticket text, and
restoring it to match the ticket would reintroduce a bug.* "Ticket X was hard" is
not a trap.

The file is **local and never committed** — it lives under `.agent/local/`, which is ignored as
a directory. It is high-churn, single-author, and a guaranteed conflict on any shared branch.
`flows/HOOKS.md` owns the prune rule that keeps it honest.

## Sessions across worktrees, and two sessions at once

`.agent/local/` is **meant to be shared across worktrees** — it holds this developer's
preferences, and those belong to the developer rather than to a checkout. Sharing it takes a
symlink the user creates (see the setup notes in the framework reference), so a plugin cannot
assume it either way.

That means **the directory does not separate worktrees**, and the session file has to separate
them itself:

```
.agent/local/cadence-session-<worktree>.md
```

`<worktree>` is the basename of the working tree's root, or a short hash of its path when two
worktrees share a basename. Two checkouts then get two files whether or not the directory is
linked — correct when it is, correct when it is not.

Three problems, and they have different answers.

### Two sessions in one working copy — a claim, not a lock

The session file carries a claim in its header:

```markdown
# Session state — <project>
updated: <YYYY-MM-DD>
claimed-by: <token>          # opaque, generated when the claim is taken
claimed-at: <ISO timestamp>
```

On `session start`, read it before writing anything:

| What you find | Do |
|---|---|
| no claim, or the claim is yours | take it: write your token and timestamp, carry on |
| a claim that is not yours, older than a day | take it, and **say so in one line** — a day-old claim is an abandoned session, not a colleague |
| a claim that is not yours and recent | **stop and offer** — see below |

A recent foreign claim means another session is live in this same working copy. Do not pick a
goal, do not move an item, and do not overwrite the file. Offer, and act on the answer:

1. **continue that session** — read its goal and keep going, which is what someone who opened a
   second terminal actually wanted;
2. **start a separate session** — write `cadence-session-2.md` (then `-3`, and so on) beside it
   and claim that;
3. **stop.**

**It is deliberately a claim rather than a lock.** A lock has to be released, and a session that
ends in a crashed terminal never releases anything — so the file would need repairing by hand,
which is worse than the problem. A claim only has to be *read*, and a stale one is
self-resolving.

### Two worktrees on the same item — only when the directory is really shared

Two worktrees can pick the same item, and a claims file only helps if both can see it. When
`.agent/local/` is linked to a shared target, it is exactly the right home; when it is not, a
claims file sitting in it coordinates nothing while looking as though it does — which is worse
than having none.

So **check, do not assume**: ask the VCS adapter for **`shared_local_dir()`** (git: inside the
common `.git`) and compare it with where `.agent/local/` actually resolves. Shared → keep one
small file there:

```markdown
<item-id>  <worktree path>  <branch>  <ISO timestamp>
```

Written when a session takes an item, removed when it releases it. On `select_goal`, skip a
candidate another worktree holds and **say which worktree holds it** — a skipped item with no
explanation looks like a priority bug.

**Not shared — or `shared_local_dir()` `unsupported` for a VCS without the concept — and the
mechanism is off.** Sessions still keep their own files, since those are keyed by worktree, but
nothing detects two worktrees on one item. Say so **once** at session start, not per candidate,
and name the one-line fix (link `.agent/local/` to the shared target). Degrading loudly beats
coordinating wrongly.

## Ownership — whose work is it

**On any project with more than one person, work belongs to someone.** That is not a feature to
switch on; it is a fact about teams, and a skill that ignores it will cheerfully suggest you pick
up something a colleague is mid-way through.

So: **ownership constrains what a session may propose, and the capacity matters as much as the
name on the item.** Being assigned something *to review* makes reviewing it yours, even though
implementing it is not — the lane says which capacity is in play, and the assignee says whose it
is. Those two together answer "may I take this", and neither answers it alone.

What follows from that is reasoning rather than a rule table, and it should stay that way:

- Work assigned to the current user is theirs to act on, in whatever capacity its lane implies.
- Unassigned work is available, and **taking it assigns it** — `update(id, {assignee: me()})`,
  where the tracker allows it. Picking up unassigned work silently is how two people start the
  same ticket, and the assignment is what makes "taken" visible to everyone else rather than only
  to the person who took it.

  **Assign when the item is taken, never while it is being proposed.** Under
  `select_goal: ai-proposes` the proposal comes first and the human confirms; assigning a
  candidate you merely considered would grab tickets on their behalf. One item, once, after the
  goal is settled.

  Where `assignee` is unsupported — or the tracker will not accept the write — **say so and carry
  on**: the work is still yours to do, it is simply not visible as taken, and the risk of a
  collision is worth one line rather than a refusal to start.
- Work assigned to somebody else is **not a candidate**. It can still be *mentioned* — as a
  blocker, as context for what you are doing — but never proposed as the goal.

Those are examples of the concept, not the concept itself. A tracker with a reviewer field, a
pairing convention, a team that rotates on-call: the question is always *can this person
legitimately act on this item now*, and the answer comes from reading the situation rather than
from matching a case in a list.

### Columns cadence does not act in

A board usually has states where the team's process continues and cadence's does not — an MR with
a peer, a QA queue, a release train. `config.tracker.hands_off` names them, each with a sentence
in the user's words about why.

**An item in a hands-off status is not a candidate, not stalled, and not yours to chase.** Those
three follow from one fact — it is somebody else's step — and each one is a mistake that would
otherwise get made: proposing it as work, reporting it as blocked, or nudging its status to keep
things moving.

**Reaching one of those statuses ends cadence's involvement with that item.** A session that hands
work off has finished with it; it does not wait, poll, or come back to it next session. Say so
once when it happens, and let the item go.

`hands_off` is populated at init by asking, because a user describing a column describes the
column rather than your involvement in it — *"what does `In Dev Review` mean"* and *"should I do
anything once something is in `In Dev Review`"* get different answers, and only the second one is
what a tool needs.

### Creating work — assign it when the owner is unambiguous

The same concept, from the other end. **A new item gets an assignee at creation when there is only
one person it could belong to.** On a single-developer project with a tracker that supports the
field, that is always the case: every ticket is theirs, and leaving a pile of unassigned items is
both noise and a lie about who is going to do them.

It also keeps *unassigned* meaningful. If unassigned is the normal state of every item, it stops
carrying information — and the rule that taking unassigned work assigns it has nothing left to
say.

On a team, the owner at creation usually **is** ambiguous, and then leaving the field empty is the
honest answer rather than a gap: planning assigns during the meeting, or whoever takes the item
assigns it then. Guessing an owner at creation is worse than leaving it open, because a wrong
assignee reads as a decision somebody made.

So the question at creation is the same one as at selection — *whose is this* — and the difference
is only whether it has an answer yet. Where the tracker does not support `assignee`, none of this
applies and nothing is lost: a single-author backlog had nothing to disambiguate anyway.

### When you cannot tell

`me()` unsupported, or `assignee` unsupported, means ownership cannot be determined. Then **say so
once** at session start and treat assignment as advisory: propose as before, and where an item
does carry an assignee that is not obviously the user, name it so a person can judge. Do **not**
guess identity from a git email — the same human is often a different principal on the tracker,
and being wrong here means confidently proposing somebody else's work.

**A single-author project needs none of this.** The `markdown` tracker declares both unsupported
precisely because a repo-backed backlog with one author has nothing to disambiguate, and the
concept then costs nothing.

## Purity & etiquette

- **Adapters perform; hooks decide.** A hook returns "create these three tickets"; the tracker adapter's `create` writes them. A custom flow can change *what* happens without touching *how* the tool is driven.
- **Least surprise.** Adapters don't push, delete, force, or rewrite history unless the operation explicitly says so. Destructive tool actions are surfaced to the user, not performed silently.
- **Config-driven, never hardcoded.** All IDs, namespaces, paths, and status names come from `config`. And **tool-generic vs project-specific**: an adapter captures how to drive the *tool* (its verbs, its universal gotchas); a project's own quirks (a machine's build path, a workspace's sync settings) belong in `config` (e.g. `vcs.gotchas`), not in the adapter — so the adapter stays clean and re-generatable.

## Model tier — adapter work runs on the cheap model

Adapter operations are **mechanical**: file and CLI mechanics with no product judgment. They're the primary target for cheap-model delegation. When a skill runs *batchy* adapter work — scanning a tracker for open items, bulk-creating tickets, parsing a large diff — it hands the work to Cadence's `mechanical` subagent (`${CLAUDE_PLUGIN_ROOT}/agents/mechanical.md`). Judgment never comes here: deciding *which* items matter or *whether* a gate passes stays on the reasoning model in the calling skill.

Rule of thumb: **delegate bulk mechanical work; keep trivial one-off ops inline** — a single `set_status` isn't worth a subagent spawn.

### The calling convention (why the tier is config and not frontmatter)

Model tiers are a binding because available models differ per user — not everyone has every tier, and IDs differ on Bedrock/Vertex. But a subagent's frontmatter is static: `agents/mechanical.md` declares `model: haiku` and cannot read the project's config. So the **caller** closes the gap:

- Read `config.models.mechanical`. If it is absent or literally `haiku`, spawn the `mechanical` subagent normally — the frontmatter default already matches.
- If it names a different tier, spawn the subagent **with an explicit per-invocation model override** set to that value. Do not edit the agent file; the plugin is never modified by a project.
- If the configured tier turns out to be unavailable, **say so and fall back to running the work inline on the session model** — then tell the user to rebind `config.models.mechanical`. A missing tier is a visible degradation, never a silent failure and never a reason to substitute a tier the user didn't choose.

`config.models.reasoning` is normally `inherit`: judgment stays on whatever model the session is already running.

## The project usually knows more than the tool does

When generating an adapter, **read what the project has already written about the
tool before interrogating the tool itself.** A team using anything unusual has
normally recorded how to drive it — in a README, a contributing guide, a
doc-system page, a convention file — and that prose carries what an interface
cannot:

- which operations are **irreversible** (a VCS with no amend; a tracker that
  cannot un-close an item),
- which recovery steps are **destructive** (a resync that reverts local edits),
- which failures **present as something else** (a status query that reports
  "synced" for a directory the tool has stopped watching).

`--help` lists verbs. It does not tell you that one of them will quietly discard
a day's work. An adapter generated only from an interface is an adapter that
knows how to call things and not when calling them is a mistake — and the
etiquette rules below (never push, never force, surface destructive actions)
depend on knowing which is which.

Inspect the interface too — it is authoritative about *what exists*, and prose
goes stale. Use the docs for judgement and the tool for verbs, **cite where each
gotcha came from**, and keep tool-generic behaviour in the adapter with
project-specific quirks in `config`.

## Generating / authoring an adapter

Adapters are normally **generated by `/cadence:init`**: it detects the tool, inspects the operations that tool actually exposes, and writes a project-local adapter implementing the relevant contract — tailored to the real verbs, namespace, and tool-generic quirks, and confirmed with the user. You can also hand-author one at `.agent/cadence/adapters/<family>/<kind>.md`, or edit a generated one. The plugin versions the *contracts*; a project owns its adapters.
